7) What happens during a session
--------------------------------
CONNECT
  -> DATA ShortsReceived remains active
  -> ANALYTICS BytesReceived is also subscribed

START
  -> ESP32 computes onboard TCN + WT + AFO + gait analytics
  -> phone computes its independent reference pipeline from the same raw DATA

BASELINE_WALK (8–18 s)
  -> normalization uses successful samples
  -> >=90% of the planned 2080 baseline samples is sufficient

WALK_MAIN transition (~18 s)
  -> both implementations lock normalization if >=1872 baseline samples arrived
  -> TCN / wavelet / gait analytics become active

STOP
  -> phone captures the final BLE raw packet tail
  -> phone performs retrospective reconciliation
  -> ESP32 performs full-session final reconciliation
  -> ESP32 sends 168-byte final summary + 144-byte IC/FC event chunks
  -> ESP32 repeats the final summary after the event chunks
  -> phone compares raw integrity, event timing, counts, and numeric metrics
  -> bottom dashboard card shows PASS / WARN / FAIL
  -> report Section 6A contains the full parity table

8) Interpretation
------------------
PASS = phone and ESP32 implementations agree within the defined contract.
WARN = raw/event integrity agrees, but at least one numeric metric exceeds its tolerance.
FAIL = at least one hard integrity check fails.

Parity is NOT ground-truth validation. After parity passes, compare the same
session with manual/video ground truth separately.
