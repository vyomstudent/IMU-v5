VSPIMU V5.8 FINAL — INSTALL / INTEGRATION ORDER
===============================================

1. ESP32 Arduino
-----------------
Use these two files in the same Arduino sketch folder:
  VSPIMU_V5_8_FINAL.ino
  gait_tcn_model.h

Do not substitute the old gait_tcn_model.h. The final header is the verified
12,864-byte tiled-workspace version with the capability-aware ESP32 allocator.

Board: ESP32 Dev Module / classic ESP32 NodeMCU
I2C: SDA GPIO21, SCL GPIO22, 400 kHz
LSM6DSO: 0x6B
Raw ODR: 208 Hz
BLE name: GAIT-V5-C3

4. Session order
-----------------
Connect -> confirm raw DATA -> START -> run all 123 s -> STOP.
Do not generate the report before finalization/parity has completed.
The dashboard's bottom parity card is the authoritative live parity display.
The report contains the same parity evidence in Section 6A.

5. Expected firmware diagnostics
---------------------------------
Look for:
  TCN SELFTEST | ... | PASS
  WARMUP READY | normalization locked | received >= 1872/2080 ...
  TASK CREATE | sample=OK flash=OK analysis=OK
  BLE ADVERTISING CONFIRMED

During a clean real session the parity hard checks require:
  ESP32 sensor misses = 0
  ESP32 raw gaps = 0
  phone missing slots = 0
  matching raw CRC-32
  matching final counts/event sets

A real sensor/I2C/BLE failure correctly appears as PARITY FAIL; it must not be
hidden by changing tolerances.

6. Validation boundary
-----------------------
TCN model parity, ESP32<->phone computational parity, and manual/video
clinical/ground-truth validation are three separate stages.

This package has passed software-only QA for JS syntax, HTML/JS DOM contract,
packet sizes, CRC path, header host self-test, ESP32 allocator smoke-compilation,
and a synthetic end-to-end parity PASS.

The only validation that cannot be performed inside this environment is the
physical ESP32 + LSM6DSO + BLE 123-second run. That must be done on the board.
