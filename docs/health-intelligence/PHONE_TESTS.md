# Capture MVP physical-phone acceptance

Status: **NOT RUN**. No Android build, install, or physical measurement is established by this checklist. Execute after a reviewed, authorized cloud build supplies a verified APK. Use engineering volunteers and synthetic motion, not patient records. Repeat every case separately on **Vivo Y29** and **Samsung Galaxy M31**; model names do not establish installed Android versions or sensor availability.

## Preparation and install

1. Record a device alias (`Y29-A`, `M31-A`), model variant, Android/API version, OS build, WebView version, APK SHA-256, source commit and cloud run URL. Do not record IMEI, serial number, Bluetooth address or personal account name. Use Settings > About phone for installed OS information. Record only the necessary OS fields.
2. Obtain `app-debug.apk` from the authorized successful build. Verify its SHA-256 against the build summary before copying it to each handset. No Android SDK or local build is needed. Keep the existing wearable firmware unchanged.
3. Open the APK using the phone's Files app. If prompted, temporarily allow **Install unknown apps** for that specific Files/browser app, install **VSPIMU Health** (`org.vspimu.health`, version `0.1.0`), then revoke that install-source allowance. Vivo commonly exposes this under Settings > Apps > Special app access; Samsung commonly uses Settings > Biometrics and security > Install unknown apps. Menu labels vary by installed OS; search Settings for the quoted permission name. Do not disable Play Protect. Report any installer rejection verbatim without personal identifiers.
4. For an upgrade, preserve existing records first and check signer compatibility. Never uninstall merely to resolve an incompatible signature: uninstall loses private records/key. A fresh-install test must use an explicitly designated disposable test handset/session.
5. Enable Bluetooth. On Android 11/API 30 and earlier, also enable the phone's Location service for BLE scanning. On Android 12/API 31 and later, the app requests Nearby devices (Bluetooth scan/connect), without a location grant. Keep the test phone within a metre of the wearable initially. Close other apps connected to the same wearable.

## Private evidence and result record

Use one row per case per phone: `case | device alias | OS/API | APK hash/commit | UTC test time | PASS/FAIL/NOT RUN | visible status | duration | counts/gaps | short error-class text`. Do not log participant identity, raw motion arrays, precise Bluetooth addresses, full session IDs, exports, filesystem contents or screenshots containing records. Use disposable-session labels T01/T02 instead of IDs. Crop screenshots to the status/control area if necessary; keep evidence local. No telemetry or external upload is authorized.

If Android system logs are already available through existing authorized tooling, restrict to this app's process and the test time window; save locally, inspect/redact before sharing, and prefer only error class/stack frame/status code. Avoid full-device bug reports, Bluetooth HCI dumps, broad logcat collections and notification/account contents. Do not add a logger that prints health payloads. A BLE packet trace, if required for MTU, uses only the synthetic test peripheral and stays local; do not record unrelated nearby devices.

Record failures as failures even when recovery works. Distinguish compilation, dashboard synthetic tests, physical acquisition, storage inspection and clinical validation. No physical acceptance claim until both phones have actual evidence; unavailable peripheral fault cases stay NOT RUN.
